# 운영 개선 방안 수립 (학습 2-1)

## 절차

1. **알려진 취약점을 확인한다.** (p.20) CVE, KISA(인터넷 침해 대응 센터) 보안 공지, 제조사 최신 패치·
   취약점. 랩: `vuln_feed`가 있으면 쓰고, 없으면 확인 못 한 출처를 '한계'에 적는다.
2. **점검 도구와 모의해킹으로 취약점을 확인한다.** (p.21) 체크리스트로 확인하고 심각도(심각·보통·단순)로
   나눠 개선 우선순위를 정한다.

   | 취약점 | 점검 방법 | 취약 판단 기준 (<표 2-4>) |
   |---|---|---|
   | 운영체제 명령 실행 | URL·파라미터에 ls, cat (윈도: dir, ipconfig) 삽입 | 명령 결과가 출력되면 취약 |
   | SQL 인젝션 | ', ", ;, #, -- 입력 / 'having 1=1-- | DB 에러 문구가 나오면 취약 |
   | SQL 인젝션 | 'and 'a'='a 와 'and 'a'='b 결과 비교 | 두 결과가 다르면 취약 |
   | SQL 인젝션(로그인) | 'or'1=1 입력 | 로그인되면 취약 |

3. **필요하면 신뢰할 수 있는 기관의 정기 점검을 받는다.** (p.21)
4. **대응 방안을 정한다.** (p.22) 최신 패치 → 없으면 다른 대응(WAF 규칙 등) → 근본 해결이 없으면
   솔루션 교체나 애플리케이션 수정(`sw-sec-dev`에 넘김)을 검토한다(<표 2-5>).
5. **개선 방안을 쓴다.** (p.23) 설정 변경 방법과 적용 확인 방법, 패치 방법과 적용 확인 방법,
   패치 후 버전 관리 대장 반영.
