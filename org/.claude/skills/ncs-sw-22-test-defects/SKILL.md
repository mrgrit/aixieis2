# SW개발 보안 테스트와 결함 관리 (학습 2-2)

목표: 구현된 응용프로그램의 결함 여부를 테스트하고, 발견된 결함을 관리한다.

## 용어 (필요 지식, pp.63-65)

- **보안 결함 등급** = 보안 사고 발생 시 복구 우선순위 = 영향도(impact) × 긴급도(urgency) (p.63)
- **테스트 종류** (<표 2-13>, p.64)

  | 구분 | 내용 | 특징 |
  |---|---|---|
  | 정적 분석 | SW를 실행하지 않고 소스코드 수준에서 분석, 개발 과정에서 사용 | 초기 발견으로 수정 비용 절감, 컴포넌트 통합 약점과 설계·구조 약점은 발견 제한 |
  | 동적 분석 | 실행 환경에서 분석, 시험 단계에서 사용 | 소스코드 불필요, 도구 사용자 수준에 영향받음, 구조 약점은 발견 불가 |

- **테스트 원칙** (p.64): 개발자와 운영자는 분리해 테스트·평가한다.
- **결함 종류** (<표 2-14>, p.65): SW보안 결함, 발견된 보안 결함(설치·운영 전), 잠재적 보안 결함(운영 환경에 전달됨),
  SW의 특이한 고장(잠재 결함이 운영 중 나타난 이상 징후).
- **결함관리 절차** (<표 2-15>, p.65): 관리계획 → 기록 → 검토 → 수정 → 재확인 → 상태 추적 → 분석·리포팅.

## 테스트 (pp.68-71)

1. 시험 단계를 수행한다 (p.68).
2. 취약점 테스트를 실시할 주기와 대상을 정한다 (p.70). 보안 팀이 SW개발 팀에 테스트를 요청한다. 신규 SW는 실운영 전에,
   운영 중인 SW는 중요 자산을 평가해 정기적으로(1달, 1년, 2년, 3년 주기) 일정을 세운다. 업무 범위·비용·일정을 합의한다.
3. 변경 요청을 제기하고 테스트 일정을 세운다 (p.71).
4. 취약점 테스트를 수행한다 (p.71).

## 결함 관리 (pp.72-77)

1. 테스트 보고서를 발행한다 (p.72).
2. 지적 사항을 해결한다 (p.73). 수정은 `change_prepare`(kind=code)로 올린다.
3. 결함 해결 사항을 보고한다 (p.74).
4. 점검이 완료된 소스코드를 관리한다 (p.76). 버전과 재진단 결과를 함께 남긴다.
5. 전반적인 보안 상황을 보고한다 (p.77).
