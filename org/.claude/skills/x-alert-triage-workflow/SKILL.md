# 경보 트리아지 (확장)

NCS 판정 절차(`ncs-log-12-analysis`)는 경보 하나를 깊게 본다. 현업 관제는 경보가 수십~수백 건씩
몰리므로, 먼저 유형별로 나누고 유형마다 정해진 증거만 빠르게 모은다. 이 스킬은 그 앞단을 맡는다.

## 1. 유형으로 나눈다 (라우팅)

| 유형 | 예 | 꼭 모을 증거 |
|---|---|---|
| W 웹 공격 | SQLi, XSS, 경로 조작, 웹셸 접근 | WAF 조치, 웹 응답 코드·크기, 같은 IP의 이전 요청 |
| A 인증 | 무차별 대입, 비정상 로그인 | 실패/성공 횟수, 성공 직후 행위, 계정의 평소 접속지 |
| N 네트워크 | 포트 스캔, 서비스 거부 | 임계치 대비 관측값, 출발지 수, 대상 포트 |
| X 유출·통신 | 대용량 외부 전송, C2 비컨 | 전송량, 주기성, 목적지, 업무 시간 여부 |
| H 호스트 | 무단 계정, 예약 작업, 권한 상승 | 생성 시각, 생성 주체, 같은 시각의 접속 로그 |

## 2. 유형별 증거를 모은다

- 표의 '꼭 모을 증거'를 도구로 조회하고, 결과마다 근거 ID(E1, E2…)를 붙인다.
- 조회 결과가 0건이면 바로 '이상 없음'으로 넘기지 않는다. ① 검색어·필드·기간을 바꿔 한 번 더,
  ② 원본 로그(`log_read`)로 한 번 더 본다. 그래도 없으면 '확인 불가'로 둔다.
  (연구에서 에이전트는 조회 결과가 비었을 때 실제 공격 경보를 더 자주 기각했다.)

## 3. 보수적으로 분류한다

- 유형별 조사 중 하나라도 대응이 필요하다는 근거가 나오면 그 경보는 **대응 필요**다.
- **대응 불필요**는 사유를 반드시 하나 고른다: 허가된 업무 / 룰 설정 오류 / 자료 오류 / 판단 불가.
  '판단 불가'는 불필요가 아니라 보류로 올린다.
- 새 증거 없이 처음 판정을 뒤집지 않는다. 다시 검토해서 판정이 바뀌면 바뀌게 만든 증거 ID를 적는다.
  (연구에서 '재검토 단계'는 맞힌 판정을 고친 경우보다 망친 경우가 더 많았다.)

## 4. 결과 표

| 경보 | 유형 | 분류 | 사유·근거 ID | 넘길 담당 |
|---|---|---|---|---|

대응 필요 경보는 `ncs-log-12-analysis`로 깊게 판정하고, 여러 건이 한 행위로 보이면 `ncs-log-22-correlation`으로 묶는다.

## 이 스킬이 NCS 절차에 더한 것

- 유형 라우팅과 유형별 필수 증거 (CORTEX의 워크플로 분기와 증거 수집 에이전트 구조를 한 사람 절차로 옮김)
- 하나라도 대응 필요면 대응 필요라는 보수적 결합 규칙 (CORTEX)
- 0건 조회 처리와 판정 번복 규칙 (Alert-Bench 실패 유형)
