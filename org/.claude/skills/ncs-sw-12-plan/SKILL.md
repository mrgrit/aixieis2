# SW개발 보안 환경 구축 일정 계획 수립 (학습 1-2)

목표: 보안성이 강화된 응용프로그램을 구현하기 위한 환경과 일정 계획을 수립한다.

## 1. 취약점 점검 환경을 분석한다 (pp.25-28)

1. 입력물을 확인한다: 취약점 점검 계획서, 취약점 점검 케이스 설계 명세서 (p.25).
2. 도구·기법으로 점검 환경 정보를 수집한다 (p.26).
3. 점검 계획서, 설계 명세서, 케이스 명세서, 절차 명세서를 검토하고 점검 목록 분석, 가정 분석, 도식화를 한다.
4. 산출물: 취약점 점검 환경 설치 및 명세서 (<표 1-14>, p.28).

## 2. 구현 계획을 수립한다 (pp.29-34)

1. **조직의 개발 업무 현황을 수집해 보안 등급으로 나눈다.** (p.29, <표 1-15> 요소별 SW개발 보안등급)

   | 보안 요소 | 등급 구분 예 |
   |---|---|
   | 기밀성 | 고객 비밀, 매우 극비, 중간적인 비밀, 대외비, 일반 정보 |
   | 무결성 | High, Middle, Low |
   | 가용성 | 1분, 시간, 1일, 1주, 1달 |

2. **SW 보안약점 7유형을 파악한다.** (pp.29-31) 진단 결과 표의 '약점 유형' 열은 이 이름을 그대로 쓴다.

   | 유형 | 학습모듈 정의 요약 |
   |---|---|
   | 입력데이터 검증 및 표현 | 입력값 사전 검증 누락, 부적절한 형식값 지정. SQL 삽입, XSS 등 |
   | 보안 기능 | 인증, 접근제어, 암호화, 기밀성, 권한 관리를 적절하지 않게 구현 |
   | 시간 및 상태 | 멀티 스레드 등에서 수행 시간과 처리 상태를 관리하지 못함 |
   | 에러처리 | 예외 처리 누락·부족, 에러 정보에 시스템 정보·상세 내역 노출 |
   | 코드 오류 | 형 변환 오류, 자원의 부적절한 반환(버퍼 오버플로) 등 개발자 실수 |
   | 캡슐화 | 은닉이 필요한 데이터·기능을 충분히 캡슐화하지 않음 |
   | API 오용 | API를 의도와 다르게 쓰거나 보안에 취약한 API를 사용 |

3. **개발 환경과 구현 계획을 세운다.** (p.31) 개발 환경: 운영 서버 접근은 보안 관리자 승인, 개발자별 개별 계정,
   권한별 독립 계정, 백신 최신화, 불필요한 인터넷 차단, 접근 암호, 외장 매체 차단.
   구현 계획: 신뢰성 높은 도구와 인가된 소프트웨어만 사용하고, 공개 SW 점검 도구를 골라 쓸 수 있다
   (<표 1-16>, p.32: SonarQube(원문 표기 'SonarCube'), SpotBugs, FindSecurityBugs, PMD, 코드레이 커뮤니티, Jenkins).
4. **조직의 보안 정책을 검토하고 보안 계획서를 쓴다.** (p.33, <표 1-17> 정책 검토 형식, <표 1-18> 보안 계획서 양식 p.33,
   <표 1-19> p.34) 랩: `policy_docs`.
