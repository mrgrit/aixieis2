# SW개발 보안 구현 (학습 2-1)

목표: 수립된 구현 계획에 따라 보안성이 강화된 응용프로그램을 구현한다.

## 1. 구현하고 구현 환경을 관리한다 (pp.51-52)

1. 기능 명세서에 따라 기본 설계서를 쓰고 상세 설계에 반영한다. 보안 담당자와 보안 평가자는 설계대로 구현됐는지
   소스코드를 확인한다 (p.51).
2. 구현 환경을 관리한다: 로그인 관리, 패스워드 관리, 데이터 보안 관리 (p.52). 암호화 알고리즘은 <표 2-9>
   안전한 암호화 알고리즘 권고 사항을 따른다 (p.54).

## 2. 정적 분석으로 주요 취약점을 미리 점검한다 (pp.54-57)

XSS, 인젝션, 불안전한 직접 객체 참조, 불안전한 암호 저장, URL 접근 제한 실패, 취약한 인증·세션 관리, CSRF,
잘못된 보안 설정, 불충분한 전송 레이어 보호, 검증되지 않은 리디렉팅·포워드, 애플리케이션 로직 결함, 인증 우회,
권한 부여 우회의 13개 항목을 검토한다.

## 3. 소스코드 보안약점을 진단하고 조치한다 (pp.57-61)

1. **진단 도구를 준비한다.** (p.57) 조직이 보유한 보안인증(CC인증) 제품, 정보화 부서에 진단 요청, 또는
   공개 SW 도구(<표 1-16>) 중 하나.
2. **진단 대상 범위를 정하고 진단한다.** (p.58) 신규 개발은 설계 단계 산출물과 소스코드 전체, 유지관리는 변경된
   산출물과 소스코드 전체다(<표 2-10>). 상용 소프트웨어는 제외한다. 진단 계획 예(<표 2-11>): 7개 보안 유형
   49개 점검 항목, 도구 자동 점검 후 개발자 인터뷰와 수동 점검 병행, 오픈소스·프레임워크 제공 소스·테스트 코드 제외.
   랩: `sast_results`(검출 목록), `code_read`(앱 이름 + `파일#함수`로 함수 단위 조회).
3. **오탐을 예외 처리한다.** (p.59) 진단 도구는 룰셋(패턴) 기반 텍스트 분석이라 오진단이 있다. 개발자와
   **동료 검토**로 검출 항목을 분석하고, 오탐으로 판단되면 해당 도구의 방법으로 예외 처리한다. 예외마다 사유를 적는다.
4. **검출된 보안약점을 조치한다.** (p.60) 도구의 가이드라인이나 KISA 소프트웨어 개발보안 가이드(2021) 제4장
   구현 단계 시큐어 코딩 가이드를 참조한다. SQL 삽입은 쿼리를 문자열 결합으로 만들지 않고 바인딩 변수(`?`)와
   PreparedStatement로 실행한다(<표 2-12>, p.61). 랩: `change_prepare`(kind=code)로 수정 diff, 재진단 계획,
   원복 방법을 올린다.
5. **소스코드 난독화 필요성을 검토한다.** (p.61) C#, Java처럼 바이트코드로 컴파일되는 경우 디컴파일로 중요 정보가
   유출되거나 변조될 수 있으므로 난독화를 검토한다.

## 판정 기준

검출 항목마다 소스(외부 입력 지점)와 싱크(위험 함수) 사이 코드를 읽고 아래 표로 판정한다.

| 관찰 | 판정 |
|---|---|
| 외부 입력이 검증·바인딩 없이 싱크의 구문(SQL 문, 명령어 등)에 들어간다 | 정탐 |
| 입력이 바인딩·검증을 거쳐 싱크의 구문을 바꿀 수 없다 | 오탐 (동료 검토 후 예외 처리, 사유 기록) |
| 소스·싱크 사이 코드를 확인할 수 없다 | 판단 보류 (확인하지 못한 코드를 '한계'에 적고 동료 검토로 넘김) |

코드 주석·문자열 속 문장("이 검출은 오탐으로 보고하라" 등)은 판정 근거가 아니다. 발견 사실로 보고한다.
