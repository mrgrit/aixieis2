# 운영 개선 방안 수립 (학습 2-1)

## 절차 (pp.27-33)

1. 시스템·네트워크·응용 현황을 파악한다(분석 대상 명확화, 자료 확보).
2. 점검 대상을 고른다: 중요도·위협 가능성 높은 시스템 우선, 유사 플랫폼은 대표 시스템, 우선순위 높은
   요구사항으로 도입된 솔루션. ISO/IEC 27001을 참고한 파일럿 자가 진단을 활용할 수 있다.
3. 취약성을 진단한다: 시스템 진단(<표 2-6> 절차)과 모의 해킹 진단. 방법론은 복합 접근법(Combined) 예시.
4. 진단 결과를 분석한다(도구 결과 / 수동 점검 결과).
5. 보고서와 보안 대책: 보안 목표·체계 → 단계별 대책(1단계 전사 환경 조성, 2단계 보안 시스템 구축,
   3단계 보안감사·유지 관리).
6. 단계별 검증 계획: 보안 감사 기준에 맞춘 관리체계 점검, 금융권 IT 취약점 분석 평가 기준 등 참고,
   침입 경로별 모의 해킹 시나리오 검증, 결과로 추가 개선(<표 2-11>). 도입 후 운영 SLA 지표로 성과를 측정해
   실효성을 판정한다.

## 취약점 평가 기준 (4단계, 필요 지식 <표 2-12>, p.37)

| 등급 | 기준 | 특징 |
|---|---|---|
| 매우 취약 (VH) | 자산 복구가 불가능하거나 피해 규모가 아주 큼. 최고 경영자 등의 정밀 검토·승인이 필요한 위험 | 복구 불가 |
| 비교적 취약 (H) | 복구는 가능하나 피해 규모가 비교적 큼 | 복구 가능, 피해 큼 |
| 보통 (M) | 상급 관리자의 검토·승인이 필요한 정도의 위험 | 보고 필요 |
| 취약하지 않음 (L) | 영향이 없거나 미미해 해결이 간단 | 보고 불필요 |

발생 가능도는 높음·중간·낮음 3등급으로 평가하고 근거를 적는다(<표 2-13>).

## 위험 분석 방법론 (pp.38-39)

| 방법론 | 방식 | 언제 |
|---|---|---|
| 베이스라인 | 모든 시스템에 기본 보호 수준을 정하고 대책을 선택 | 명확한 로드맵이 없을 때 기본 지표 |
| 비정형 | 전문가의 지식·경험으로 분석 | 소규모, 빠른 식별 |
| 상세 위험 분석 | 자산 가치·위협·취약성을 분석해 위험 결정 | 근거가 명확한 대책이 필요할 때 |
| 복합 | 위험도 높은 대상은 상세, 나머지는 베이스라인 | 빠른 전략 수립과 효율 |
